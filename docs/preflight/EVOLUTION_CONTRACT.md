**IMPORTANT**: The existing `facilcar` Evolution instance is used for **catalog import** (vendor-to-store catalog messages). The SDR must use a **separate instance** connected to the customer-facing WhatsApp number (`5545999974232` production, `5545988432998` development).

Evolution API v2.3.7 supports multiple instances. Both can run in the same container.

## Webhook Model

Evolution sends webhooks to a configured URL per instance. The SDR ingress endpoint will be separate from the catalog import endpoint.

### Webhook Payload Structure (v2 — confirmed from parse code)

```json
{
  "event": "MESSAGES_UPSERT",
  "instance": "facilcar-sdr",
  "data": {
    "key": {
      "remoteJid": "5545988432998@s.whatsapp.net",
      "fromMe": false,
      "id": "3EB0C6D1234567890123"
    },
    "message": {
      "conversation": "Quero comprar um carro"
    },
    "messageTimestamp": 1724628000
  }
}
```

### Alternative payload shapes handled by existing parse code:
- `data` as array of message objects
- `data.messages` as array
- Top-level `key` / `message` fallback
- `date_time` as timestamp fallback

### Message Types Handled

| Type | Field | SDR Notes |
|------|-------|-----------|
| Text | `message.conversation` | Primary |
| Extended text (links, formatting) | `message.extendedTextMessage.text` | Primary |
| Image with caption | `message.imageMessage.caption` | Caption as text; image as media |
| Video with caption | `message.videoMessage.caption` | Caption as text |
| Document with caption | `message.documentMessage.caption` | Caption as text; doc as media |
| Audio | `message.audioMessage` | Media type; needs transcription |
| Sticker | `message.stickerMessage` | Ignore for SDR |
| Product catalog | `message.productMessage.product` | Not expected in customer conversations |

## JID Normalization (from `normalize-jid.ts`)

The existing normalization is correct and reusable:

```
remoteJid: "5545988432998@s.whatsapp.net" → "5545988432998"
remoteJid: "5545988432998@g.us"           → GROUP — must be blocked for SDR
remoteJid: "abc123@lid"                   → LID (use remoteJidAlt as phone fallback)
remoteJid: "5511999:12@s.whatsapp.net"    → "5511999" (device suffix stripped)
```

**Group guard**: Any JID ending in `@g.us` is a WhatsApp group. The SDR MUST reject group messages at ingress. Groups must never enter the sales flow.

**LID handling**: Meta is rolling out opaque LID-based JIDs. When `remoteJid` ends in `@lid`, use `remoteJidAlt` (the phone-based JID) as canonical identity. The parse code already handles this.

**Canonical phone format**: digits only, 10–15 chars (Brazilian: 13 digits with country code, e.g., `5545988432998`).

## fromMe Detection

`key.fromMe = true` means the message was sent FROM the WhatsApp instance (i.e., a seller typing on the device or via API).

**SDR rule**: A `fromMe=true` message from a HUMAN (not bot-generated) MUST transition the thread to `HUMAN_ACTIVE`. This prevents bot/human collision.

**Implementation**: The SDR ingress must classify each `fromMe=true` message:
- If generated by the SDR itself (track outgoing message IDs): ignore for state transition
- If NOT generated by SDR (seller-typed): trigger `HUMAN_ACTIVE` transition immediately

One pragmatic approach: track all message IDs sent by the SDR API. Any `fromMe=true` with an unknown ID is assumed human.

## Media Handling

### Download
Evolution v2 media download:
```
GET /chat/getBase64FromMediaMessage/{instanceName}
Body: { "message": { <rawMediaRef> } }
Response: { "base64": "...", "mimetype": "image/jpeg" }
```

Or via direct media URL (if S3 enabled in Evolution, not enabled in current config).

**Current config**: `S3_ENABLED=false` — media must be downloaded via API base64 endpoint.

### SDR Media Strategy (per doc priority)
1. **Images** (CNH, CRLV, photos): Download → OpenAI Vision → extract structured data → store original in private bucket
2. **Audio**: Download → OpenAI Whisper (`audio/transcriptions`) → treat as text
3. **Documents** (PDF holerite, comprovante): Download → OpenAI Files API or Vision → extract fields
4. **Video**: Extract caption text only (ignore video for MVP)
5. **Sticker**: Ignore

## Sending Messages

### Send Text
```
POST /message/sendText/{instanceName}
Headers: { apikey: <key> }
Body: {
  "number": "5545988432998",
  "text": "Olá! 👋 Aqui é a Júlia da FacilCar...",
  "delay": 1000
}
```

### Send Media (Image)
```
POST /message/sendMedia/{instanceName}
Body: {
  "number": "5545988432998",
  "mediatype": "image",
  "mimetype": "image/jpeg",
  "media": "<base64 or URL>",
  "caption": "Confira este veículo:"
}
```

## Reconnect / Reliability

- Evolution persists session state in its own Postgres (`DATABASE_SAVE_DATA_INSTANCE=true`)
- Restart policy: `unless-stopped` in docker-compose
- Redis cache enabled (`CACHE_REDIS_ENABLED=true`)
- On reconnect: Evolution re-registers webhook; no manual action needed
- Companion fingerprint: Chrome/Chrome — do NOT change without testing (fingerprint affects QR scan stability)

## Webhook Authentication Strategy for SDR

The catalog import webhook uses `CATALOG_IMPORT_SECRET` via `assertCatalogImportSecret()`. The SDR webhook should use the same pattern with a separate secret:

```
SDR_WEBHOOK_SECRET=<random-string>
```

Header: `x-sdr-secret: <value>` or reuse Evolution's own `apikey` header scheme with a different key.

## Evolution API Client (Python)

The Python SDR service will need an HTTP client to:
1. Receive webhooks (FastAPI endpoint)
2. Send text messages
3. Send media
4. Download media (base64)
5. Check instance status

Recommended: `httpx` async client. Wrap in a thin `EvolutionClient` class with retry logic and exponential backoff.
